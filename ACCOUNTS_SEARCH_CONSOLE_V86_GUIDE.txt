1. THE REQUEST
------------------------------------------------------------------------------
"Accounts — Account Management. Can you create a search button/tab so that I
can easily determine the accounts, due to many accounts included in the system,
the search bar or button can make an easy access to the accounts that I need
to — and actions. Make it professionally made."

Before V86 the Account Management page rendered every registered account in one
long scrollable table. Finding one person meant scrolling and reading row after
row, and the approval queue (accounts still waiting for a role + Approve) was
buried somewhere inside the list.

2. WHAT WAS BUILT
------------------------------------------------------------------------------
A search console sits directly above the accounts table, inside the existing
Account Management panel:

  * FIND AN ACCOUNT — instant search as you type. It looks at:
      - account display name          - username            - optional email
      - role                          - linked member (name, membership ID,
                                        student number, Outlook, section,
                                        instrument, period group)
      - approving / rejecting officer - request, approval and last sign-in dates
      - plain-language status words ("pending", "awaiting", "disabled",
        "deactivated", "never signed in", …)
    Typing is accent-insensitive ("munoz" finds "Muñoz") and space-separated
    terms must all match, so "beatriz lacsamana" finds exactly that account.
    Every match is highlighted in the table.

  * STATUS TABS WITH LIVE COUNTS — All accounts / Needs approval / Active /
    Rejected / Disabled. The counts are computed from the accounts the page is
    already showing, so the approval queue is always one click away.

  * ROLE FILTER — every role that exists in the account list plus the roles the
    system defines ("All roles" by default).

  * SORT — Priority (the same action-first order Account Management already
    uses: pending accounts first, newest request first), Account name (A–Z),
    Role (A–Z), Newest request first, Recently approved, Most recent sign-in.
    Sorting only re-orders the rows that are already rendered; it never hides or
    rebuilds them.

  * SUMMARY LINE — "7 of 42 accounts shown • Status: Needs approval • Role:
    Staff Account • Search: "cruz" • Press Enter to jump to the first match", so
    the officer always knows exactly what the table is showing.

  * EMPTY STATE — when nothing matches, an explicit panel states the active
    filter, confirms that nothing was changed, and offers "Clear search and
    filters" instead of leaving a blank table.

  * KEYBOARD — Enter jumps to (and flashes) the first match, and moves focus
    onto that account's controls when exactly one account matches; Esc clears
    the search (or the filters); Ctrl + K (⌘ + K on Apple devices) returns to
    the search field from anywhere on the page; the status tabs support
    ArrowLeft / ArrowRight / Home / End. The shortcut is printed next to the
    field, and all of it is announced through polite live regions.

  * RESET FILTERS — a one-click return to the full list; the button only appears
    while a filter is active.

3. WHY IT IS SAFE
------------------------------------------------------------------------------
  * READ ONLY. The console never calls saveAccounts / deleteAccount and never
    mutates an account object. It reads the list through
    window.LSOAuth.loadAccounts() (already a defensive copy).
  * management-attendance-member-info-v4.js is NOT modified. renderAccounts()
    still owns the markup, the role and linked-member selects, the
    Approve / Reject / Enable / Delete buttons, and the delegated change/click
    listeners on #accountsTableBody.
  * No row is ever rebuilt or removed. Filtering only toggles the
    .accounts-row-filtered-out class (display: none), so every action keeps its
    listener, its selected value and its busy state; sorting only moves the same
    <tr> nodes. Nothing is reordered while a row has focus, so an officer's
    dropdown can never jump away mid-edit.
  * Alert deep-links keep working. "Review Account" in the Action Center clears
    the console filters in the capture phase, before the routing handler starts
    its 60 ms refresh + scroll-to-row, so the targeted account can never stay
    hidden behind a stale filter.
  * Permission model untouched: no role, permission, landing-page or database
    write path is involved. The console appears only when the Accounts table
    actually has data rows (i.e. an authorised Administrator) and stays hidden
    otherwise — including for every other role.

4. HOW TO USE IT
------------------------------------------------------------------------------
  1. Open Accounts → Account Management.
  2. Type any part of a name, username, email, role or linked member in
     "Find an account". The table narrows as you type (click ✕ to clear).
  3. To work the approval queue, click the "Needs approval" tab, choose the role
     and the linked member for each pending account, then press Approve exactly
     as before.
  4. Use Role / Sort by to focus a batch, then Reset filters to return to the
     full, action-first list.
  5. Press Enter after typing to jump to the first match; press Esc to clear;
     press Ctrl + K from anywhere on the page to return to the search field.
